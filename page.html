CHAPTER 01 · 结论

结论与三处关键修正

声之建筑值得做，而且比 11.07 那版判断更强。三条新依据：①竞品三队全部没有空间音频——官方硬指标点名的那一条，是 A 队（空间社交）、B 队（AI 校园）、C 队（机器人实验室）都没碰的位置；②空间音频是 Spatial SDK 的核心能力，不是实验性 API，不需要 pico.spatial.use_experimental_api，不要求 PICO OS 6，不依赖 SpatialML；③零外部依赖——不需要后端、账号、网络、模型下载、3D 资产，只需要一段 60 秒录音。

唯一真正的死穴 空间音频的听感（方向、距离、指向性）只能在头显上验证，模拟器只能验证「声音在播、坐标在动」。

止损线提前到 W2：若 11.22（W2 结束）仍无法在真机上验证声源定位，立即切方向 D。 理由不变且更硬：拿不到的设备不会因为再等一周就来；而 D 的全部分数都不依赖它。

1.1为什么现在做这个方向

独占一条官方硬指标空间音频在官方五条硬指标里点名，且三支竞品队伍一个都没做。这是唯一能「独占」的位置——不是做得更好，是别人根本没碰。
技术门槛反而更低空间音频是核心 SDK 能力（ObjectAudioComponent / AmbientAudioComponent / Directivity / AudioEvents），不需要实验性标志，不依赖 OS 6。而「拍照变山」那条路依赖 SpatialML → 要求 OS 6 → PICO 4 Ultra（OS5）可能整个用不了。
媒介不可替代声音的方向性、远近、指向性在 2D 屏幕上不存在。评委戴上头显转一圈就能听出空间结构——这是屏幕永远做不到的，也是「只有 XR 能做」的硬证明。
零外部依赖不需要后端服务、账号体系、网络请求、模型下载、3D 资产库、Tripo。演示现场断网照常跑——而竞品三队全部依赖后端或 LLM，断网即崩。
评委能亲手参与转身找声源、绕到柱背后听变化——这是「体验」而不只是「观看」。三队的最小交付都是线性点击流程。
可自证深度作品可溯源：公开仓库 + 内核单测 + 安装包与 Commit ID 一一对应。路线为「一个人做的」这一质疑的正面答案。

1.2与 11.07 概念稿的三处关键修正

方案书 §4 的概念稿写于 11.07。本轮逐条核对了官方 SDK 6.1 的 agent-vault 文档，发现三处必须修正的设计错误，其中一处是根本性的。

修正原稿写法核实后为什么必须改
① 主窗形态
根本性		 24 根柱子放在半径 1.6 m 的环上，装在 Volumetric 主窗里 主窗必须是 Stage 沉浸场景（DefaultStage），3 个副窗维持 Planar 窗口体实测 0.768 m 立方、X 方向可见仅 ±0.384 m，1.6 m 的环根本放不下，只有正前方约 ±120° 露得出来且柱子会被切边。官方「Create immersive spatial audio」样例用的就是 DefaultStage + Planar 控制面板——声源能绕着你走，前提是它是 Stage

还有一处原稿说错了，这里更正 §4 写「影像内核的直方图 / 缺陷判据可以扔掉」——扔的是语义，不是骨架。 Frame → Analyzer → Field → MeshBuilder → MeshModel 这套分层照抄给音频侧（AudioFrame → SpectrumAnalyzer → EnergyField → ColumnMeshBuilder），连同 42 个内核单测的测试基建一起转过去。详见第 8 章。

CHAPTER 03 · 机制

作品机制与「显影」开场

♪
SONOSPHERE

声之建筑

听见的每一秒，在空间里长出会发声的建筑。

一段 60 秒的声音被切成 24 片，绕着你立成 24 根柱子。柱子越高，那一刻的能量越强；每根柱子都是一个真实声源，你绕着建筑走，声音也跟着转。

3.1基本映射

输入 / 元素映射评委能读出什么
60 秒真实音频切成 24 片（每片 2.5 秒）时间有结构了——不是一条连续的流，是可以被「立起来」的 24 个瞬间
一根柱子= 一片（24 根，等角分布成环，半径 1.6 m）「一根柱子 = 一秒」——路演首句就说清
柱高= 该片总能量（0.15 – 1.4 m）响的地方高，静的地方矮 —— 建筑的轮廓就是这段声音的动态
柱色= 频谱重心：低频深琥珀 / 中频橙 / 高频冷白不用看数据也能感到「这段声音是沉的还是脆的」
柱面纹理= 该片 24 频带能量的竖条（128 列 → 24 格，烘焙进贴图）凑近看，每根柱子内部也有结构 —— 细节是「真做出来的」的信号
柱顶标签= 时间码 / 频段 / 响度 dB可读 = 可讨论。评委能指着某根柱问「这段是什么」
地面光环同心光环 = 时间轴，当前播放位置那圈亮起「现在听到的是第几秒」——空间化的进度条

3.2建筑感的三层（缺一层就退化成「声音可视化」）

「把声音画成柱子」本身并不稀奇，任何频谱可视化都能做。让它成为「建筑」的，是下面三层叠起来。

层手段评委感知为什么这一层不可省
几何层Stage 沉浸场景 + 24 柱环形 + 地面声呐光环 + 暗场「我站在一圈柱子中间」只有 Stage 能让声源绕着你走；窗口体放不下这个环
指向层Directivity(pattern, sharpness) 逐柱不同「我绕到这根柱子后面，它变闷了」这是「声音真的在那个位置」最省力也最难反驳的证明——不是音效在循环，是有方向的声源
混响层reverbVolume + AudioMixerGroupResource.setVolume()「整个空间的大小 / 材质在变」同一个声音换个混响 = 换了个房间。这一层直接命中「建筑」的语义
指向层的额外收益 让低频柱用更全向的 pattern、高频柱用更聚焦的，评委就能听出这是两套不同的空间线索：低频包裹感强、高频定位感极强。 这是零成本的设计判断，但听起来立刻「专业」。

3.3开场仪式：把「显影」做成一个参数

官方 Stage 有四种 style，其中 Progressive 可以用 immersion（0–100）连续调节「真实环境透传」与「虚拟场景」的比例：

immersion = 0 → 几乎纯真实房间，虚拟实体不可见 immersion = 50 → 真实环境与虚拟场景各占一半（真实环境的光照仍来自 VST） immersion = 100 → 等价于 Full：纯虚拟场景，真实环境被完全遮住
这就是「显影」本身 immersion 从 0 推到 100：你眼前的客厅像一张照片在显影液里慢慢浮出，变成由声音构成的建筑。

不需要任何模型、贴图或动画资产——只需要一个参数在 6 秒内推过去。这是零资产成本、零外部依赖、且在模拟器上就能验收的戏剧性开场。

CHAPTER 04 · 引擎

空间音频引擎（官方 API 核对）

本章每一个 API 名与参数都来自本机 PICO SDK 6.1 的 agent-vault 官方文档（com.pico.spatial.core.ecs.audio / com.pico.spatial.audio），不是凭记忆写的。底层用 HRTF 渲染：「models the acoustic characteristics of the human ear based on HRTF」。

为什么这一章最重要 空间音频是核心 SDK 能力，不是实验性 API —— 不需要 pico.spatial.use_experimental_api，不要求 PICO OS 6，不依赖 SpatialML。 这意味着它的真机门槛比「拍照变山」那条路低得多（那条要 OS 6，4 Ultra 是 OS 5）。

4.1API 清单与参数

API包用途与关键参数

4.2核心代码骨架

柱子实体就是声源 —— ObjectAudioComponent 直接挂在柱子的 Entity 上。这样柱阵旋转 / 缩放时，声音位置自动跟着走，不需要任何额外同步代码。

// 柱子 = 声源 val column = Entity() column.components.set( ObjectAudioComponent( volume = 1.0f, Directivity(pattern = 0.35f, sharpness = 0.60f), distanceAttenuationMode = DistanceAttenuationMode.INVERSE_SQUARED, reverbVolume = 0.5f ) ) val player = column.prepareAudio(audioResource) // AudioPlayerController player.play()

官方文档给出的等价写法（第三方的 AudioTrack / ExoPlayer / MediaPlayer 也能接）：

val extension = SpatialAudioTrackExtension() extension.spatialAudioTrackExtensionConfig( mode = SpatialAudioMode.OBJECT, isAmbisonic = false, builder = audioTrackBuilder ) extension.attachToEntityWithBuilder(targetEntity, audioTrackBuilder) val audioTrack = audioTrackBuilder.build()

4.3声源策略

24 柱 = 24 个潜在声源但同时只激活能量最高的 4 个。理由有两条：一是性能（24 路空间化渲染 + 衰减计算）；二是听感清晰（同时响 24 个会糊成一片，评委反而听不出方向）。
声源实体即柱子ObjectAudioComponent 挂在柱 Entity 上 ⇒ 柱阵变换时声音位置自动跟随，无需同步代码。
资源统一管理24 段音频用 AudioResourceLibraryComponent 管理；播放头推进靠 AudioEvents。
切换要交叉淡化换声源时用 AudioMixerGroupResource.setVolume() 做淡入淡出，否则会出现爆音 —— 爆音在评委的耳朵里是致命的。
不做实时麦克风采集输入是文件回放。理由：模拟器无麦克风；回放可复现、可调试、可在提交包内自洽（不依赖任何授权）。
频段决定指向性低频柱 pattern 更全向（包裹感），高频柱 pattern 更聚焦（定位感）。零成本，但听起来立刻专业。
六维预估：声之建筑 vs 曝光暗房
声之建筑的优势集中在「创新」与「交互体验」两维 —— 前者来自独占空间音频硬指标，后者来自评委可亲身参与。

CHAPTER 06 · 内核

音频内核与素材

6.1音频内核：与影像内核同构

新建 app/audio-core/——纯 Kotlin、零 Android 依赖，与 imaging-core 一样可在 PC 侧跑单测。分层照抄影像内核的写法：

AudioFrame (PCM) → SpectrumAnalyzer → EnergyField(24×24) → ColumnLayout → (Stage 实体 + 声源)
层做什么输出与验收
AudioFramePCM 帧容器（样本率 / 声道 / 时间戳）与影像内核的 Frame 同构
SpectrumAnalyzer分帧 + 梅尔频谱60 s → 24 段，每段 24 个频带 ⇒ 24 × 24 能量矩阵
EnergyField每段特征量提取总能量 / 频谱重心 / 瞬态密度 / 高频占比 / 房间感指标
RoomTone房间感指标计算频谱平坦度 + 高频衰减斜率的组合。混响多、空间大的录音给出不同的值 ⇒ 直接映射到 reverbVolume 与柱体「材质」
单测（≥12 条，镜像影像内核的测试风格） 静音输入全零 · 纯正弦的重心正确 · 脉冲串的瞬态密度正确 · 削波输入不越界 · 立体声左右不平衡的处理 · 时长边界（不足 / 超出 24 片）· 分段边界不重复不丢样 · 矩阵维度恒定 ……
这是「完成度 10 分」与原创性护栏的共同证据 —— 公开仓库里能跑绿的测试，比任何自述都有说服力。

6.3录音指导（决定成败）

✅ 要有强起伏说话、脚步、开关门、远处雷声 —— 起伏越大，柱高差异越大，视觉越有故事
✅ 在真实空间里录客厅 / 走廊 / 楼道 —— 空间混响本身就是我们要分析的「房间感指标」
❌ 不要纯音乐音乐频谱过于平稳，柱子会长得一样，视觉就没戏
❌ 不要持续噪声雨声、空调声全程一样 ⇒ 24 根柱子几乎等高，「建筑」变成「栅栏」
📱 设备不限手机录即可。要求只有两条：时长 60 秒、没有背景音乐
🔒 合规只用自己录的声音。街道录音避免拍到可识别人脸与清晰对话
✓零外部素材——无模型下载、无 3D 资产、无第三方图库、无 Tripo API。这是本方向相对「指尖造物」的最大优势：没有拿不到就做不完的环节。

若 11.22 真机验证失败：切 D。此时 D 的现成资产（曝光山脉 + 四窗口 + 42 单测 + 提交历史）全部还在，切过去是 1 天的成本，不是 3 周。这个「先 A 后 D」的顺序是风险最低的。

一句话判断

声之建筑是四方向里天花板最高、且唯一独占一条官方硬指标的一个。它的难处不在想法，在「能不能在真机上被听见」——所以整份方案的重量都压在 11.20 那次真机预约上。

放弃信号：11.22 仍无法在真机验证声源定位。此时切方向 D，不是因为 D 更好，而是因为拿不到的设备不会因为再等一周就来。

反过来说，只要 11.20 能戴上头显听到「绕到柱背声音变闷」，这个方向就没有理由再犹豫 —— 那时候真正要花力气的是把它做得更好看、更完整，而不是再比较方向。
