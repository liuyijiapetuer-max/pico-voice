决策建议

按 A 执行，11.22 设硬止损闸门。

理由：A 同时在「独占硬指标」和「硬件门槛」两条上占优，而这两条正是 D 的软肋。且 A 的止损线可判定（真机验不出定位就切），D 的止损线模糊。

若 11.22 真机验证失败：切 D。此时 D 的现成资产（曝光山脉 + 四窗口 + 42 单测 + 提交历史）全部还在，切过去是 1 天的成本，不是 3 周。这个「先 A 后 D」的顺序是风险最低的。

8.5路演脚本（30 秒版）

时间动作与台词
0–3 s「这是一段真实录音。」
3–6 s（immersion 从 0 推到 100）「这是我家客厅 —— 现在它在显影。」
6–12 s24 根柱子从地面升起，柱子随声音呼吸。「60 秒，被切成了 24 根柱子。一根柱子是一秒。」
12–18 s4 个声源同时响，评委不由自主转头。「你现在听到的方向，是真的方向。」
18–24 s（走到某根柱背后）声音变闷。「我绕到它背后 —— 你听，它变了。」
24–30 s（转向评委）「声音不是被播放的，是被建造的。」

8.6评委最可能问的 5 个问题

问题回答要点
这是真录音吗？是，自己用手机录的。刻意保留底噪与手机麦克风的质感——这是「真实」的证据
声音定位是 SDK 自带还是你自己做的？SDK 内建（HRTF 渲染 + ObjectAudioComponent）。我做的是「把声音映射成建筑」这一层——分析、分段、生成几何、挂声源
这套能用在游戏里吗？能，ObjectAudioComponent 本来就是给游戏用的（官方文档的 VR 游戏用例就是这个）。我做的是「让声音变成可走进去的空间对象」
你一个人做的？是。作品可溯源：公开仓库 + 内核单测 + 安装包与 Commit ID 一一对应（评分本来就以安装包 + Commit ID 为依据）
和普通声音可视化有什么区别？普通可视化是看频谱；这个是走进去，而且绕到背面声音真的变——屏幕做不到
